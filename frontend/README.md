# LegalSearch — фронтенд

Интерфейс поиска и анализа судебной практики на Next.js 16. Стили перенесены
из прототипа `LegalSearch_interface.html` (`src/app/globals.css`), порядок
экранов — по описанию автора прототипа (см. «Логика продукта»). Сам прототип в
репозиторий не входит.

## Запуск

```bash
npm install
npm run mock   # mock-API на :8000 — демонстрационные данные из эталона
npm run dev    # интерфейс на http://localhost:3000 (вход — любой email/пароль на mock)
```

Чтобы работать с настоящим backend, запустите его на `:8000` вместо `npm run mock`
или укажите адрес в `NEXT_PUBLIC_API_URL`. С текущим backend работают вход, поиск
(вывод LLM со сносками `[n]` и список найденных фрагментов), история и папки;
статистика практики, схема вывода и сравнение покажут «нет данных», пока
backend не начнёт отдавать анализ (см. «API»).

Интерфейс рассчитан на частично реализованный контракт: недостающие поля
заполняются пустыми значениями в `src/lib/api.ts`, ошибки сервера показываются
по-русски с кнопкой «Повторить», 401 возвращает на страницу входа, сбой сети при
проверке сессии не разлогинивает.

## Тесты

```bash
npm run lint
npx tsc --noEmit
npm run test:e2e   # Playwright: сам соберёт приложение и поднимет свой mock на :3010/:8010
```

E2E-тесты используют установленный Google Chrome (`channel: "chrome"`), браузеры
Playwright скачивать не нужно. Любая ошибка в консоли браузера валит тест.
`e2e/app.spec.ts` — сценарии экранов эталона, `e2e/robustness.spec.ts` — сбои и
неполные ответы backend (подменяются через `page.route`).

## Демо-стенд

`deploy/deploy.sh` собирает standalone-версию локально и поднимает на сервере
два контейнера — интерфейс и API (за тем же доменом на `/api`).
Сервер должен иметь Docker и общий Caddy, подключающий сайты из
`sites/*.caddy` и видящий приложения в docker-сети `web`:

```bash
DEPLOY_HOST=root@server DEMO_DOMAIN=demo.example.com ./deploy/deploy.sh
```

- **Доступ — по общему паролю** (HTTP Basic в Caddy): адрес стенда попадает в публичные
  журналы сертификатов, а API тратит бесплатную квоту GigaChat. Логин и bcrypt-хеш —
  в `.env.demo`: `DEMO_AUTH_USER`, `DEMO_AUTH_HASH` (хеш: `caddy hash-password`),
  `DEMO_AUTH_PASSWORD` — для проверки после выкладки. Без них скрипт откажется
  выкладывать (`ALLOW_PUBLIC=1` — осознанно без пароля). Токен приложения в демо-сборке
  идёт в `X-Auth-Token` (`NEXT_PUBLIC_AUTH_HEADER`), потому что `Authorization` занят паролем.
- Без собранного корпуса скрипт тоже остановится (`ALLOW_FIXTURE=1` — выложить
  демонстрационную выдачу).
- Выкладка: новые контейнеры → ожидание healthcheck → при неудаче откат на прежние образы;
  затем файл сайта в Caddy (`validate` + `reload`, при ошибке — откат файла); снаружи
  проверяется, что без пароля 401, а с паролем `/api/health` отвечает.
- Сервер общий с другими сайтами: у контейнеров лимиты памяти, CPU и процессов, логи
  с ротацией; старые образы стенда удаляются (только по метке `org.legalsearch.demo`).
- Вход в приложение принимает любые email и пароль; у каждого email свои история,
  папки и избранное (в памяти — перезапуск `legalsearch-api` их сбрасывает).
- Ограничения API: тело запроса до 64 КБ, поисковый запрос до 1000 символов, до 50 папок,
  200 документов в папке и в избранном; CORS — только для локальной разработки.

## Демо-поиск по реальным решениям (`demo-api/`)

Вместо фиксированной выдачи API может искать по корпусу настоящих судебных актов:
эмбеддинги `Xenova/multilingual-e5-small` (ONNX, CPU, через transformers.js) и
анализ через GigaChat API (бесплатный freemium для физлиц, модель `GigaChat-3-Ultra`).

```bash
cd demo-api && npm install
# 1. PDF решений (с текстовым слоем) — в demo-api/data/pdf/
# 2. ключ GigaChat — в frontend/.env.demo: GIGACHAT_AUTH_KEY=…
node --env-file=../.env.demo ingest/run.mjs      # текст → разбор GigaChat → эмбеддинги
cd .. && CORPUS_DIR=demo-api/data/corpus node --env-file=.env.demo mock/server.mjs
```

- Суд, дата, номер дела и вид акта берутся из шапки PDF; суть, обстоятельства, позиция,
  итог и цитата — разбор GigaChat, один раз при сборке (≈ 10 с и ≈ 7,5 тыс. токенов на акт).
  Цитата проверяется по тексту: если модель пересказала фрагмент, показывается ближайший
  отрывок, который в акте действительно есть; если такого нет — блок цитаты скрыт.
- Повторная сборка (`node ingest/run.mjs`) GigaChat не вызывает: текст и шапка
  пересчитываются каждый раз, а разбор хранится в `data/annotations/` под id = хеш исходного
  текста PDF (от правил очистки не зависит); `--force` разбирает GigaChat заново. Тексты
  удалённых PDF из корпуса убираются.
- Отбор актов: номер дела в запросе (`А40-256905/2023`) — сразу это дело, без LLM; иначе
  косинус e5 ≥ `MIN_COSINE` (0.85) **и** в акте есть большая часть значимых слов запроса
  с весом по их редкости (`MIN_COVERAGE` 0.5). На корпусе из 56 постановлений одного
  косинуса мало: вопрос не по теме («ипотека», «штраф ГИБДД») доходит до 0.85–0.87, а
  лексическая проверка отсекает его — «ничего не найдено». При другом корпусе пороги
  стоит перепроверить (`engine.retrieve`).
- На запрос: «Краткий вывод» и анализ (схема вывода, совпадения/отличия, «почему
  релевантен») от GigaChat. У физлица один поток — запросы идут по очереди (до
  `GIGACHAT_MAX_QUEUE`=6 ждущих, дальше «сервис занят»), у каждого вызова дедлайн
  `GIGACHAT_TIMEOUT_MS`=45 с; запросы ушедших клиентов не выполняются; одинаковые
  запросы, пришедшие одновременно, выполняются один раз.
- Кеш ответов: только id найденных актов, вывод и анализ (без текстов), до 500 запросов,
  атомарная запись; пустые, отфильтрованные и обрезанные ответы не кешируются.
- Сертификат НУЦ Минцифры (`demo-api/certs`) используется только для запросов к GigaChat.
- `deploy/deploy.sh` выкладывает корпус и ключ вместе со стендом.

## Логика продукта

Визуальный язык — из прототипа, а порядок экранов — по описанию его автора:

1. Юрист вводит запрос → **краткая сводка**: краткий вывод, статистика практики
   и под ними вся выдача документов, у каждого — оценка применимости (релевантность).
2. Стрелка «Развернуть логику» у вывода → **схема вывода**: из чего вывод сложился
   и что из него следует; оттуда — обратно к выдаче. Сводка, документы и схема —
   это одна вкладка «Поисковая выдача»; вторая вкладка — «Сравнительная таблица».
3. Из выдачи — в **карточку документа**: что совпадает с делом юриста, что
   отличается, почему документ релевантен. Гипотеза: по карточке можно решить,
   подходит ли дело, не открывая документ. Клик по цитате открывает полный текст
   документа на этом месте, с подсветкой.
4. Документ можно добавить **«В сравнение»** — отобранные дела сопоставляются в
   **сравнительной таблице** (новый поиск начинает новую таблицу — анализ дел
   строится относительно запроса), — сохранить в **избранное** или в **папку**.

## Экраны

| Маршрут | Экран |
|---|---|
| `/` | Главная: поиск, примеры запросов, последние запросы |
| `/summary` | Краткая сводка: вывод (стримится, сноски `[n]` — ссылки на документы), статистика, вся выдача с сортировкой и фильтрами |
| `/map` | Схема вывода (7 блоков) — открывается стрелкой у краткого вывода |
| `/compare` | Сравнительная таблица: дела, добавленные кнопкой «В сравнение», против «моего дела» |
| `/documents/[id]` | Карточка документа: совпадения, отличия, почему релевантен, ключевой фрагмент → полный текст |
| `/favorites` | Избранное |
| `/history` | История запросов |
| `/folders`, `/folders/[id]` | Папки (в backend — collections) |
| `/login`, `/register` | Вход и регистрация (в прототипе их нет, оформлены в его стиле) |

`/documents` (бывший экран «Все документы» прототипа) перенаправляет к выдаче на `/summary`.

Состояние текущей выдачи хранится в `src/lib/search-context.tsx` (переживает
перезагрузку страницы — sessionStorage), библиотека пользователя (папки,
избранное, история) — в `src/lib/library-context.tsx`.

## API

Типы — `src/lib/types.ts`, клиент — `src/lib/api.ts`, эталонная реализация —
`mock/server.mjs`.

| Эндпоинт | Что делает | В backend |
|---|---|---|
| `POST /auth/login`, `/auth/register`, `GET /auth/me` | авторизация | есть |
| `POST /telemetry/events` | журнал действий | есть |
| `POST /search/` (SSE) | поиск, см. события ниже | **нужно изменить** |
| `GET /cases/{id}?query_id=` | карточка дела с анализом относительно запроса | **нужно добавить** |
| `GET /history/` | история запросов | есть |
| `DELETE /history/` | очистить историю | **нужно добавить** |
| `GET/POST /collections/`, `PATCH/DELETE /collections/{id}` | папки | есть; **добавить поле `description`** |
| `POST /collections/{id}/items`, `DELETE …/items/{item_id}` | документы в папке | есть; **добавить поля `court`, `date`** |
| `GET /favorites/`, `PUT/DELETE /favorites/{id}` | избранное | **нужно добавить** |

События потока `POST /search/` (`text/event-stream`):

| Событие | Данные | Когда |
|---|---|---|
| `cases` | `{cases: CaseDetail[], demo: boolean}` | один раз, первым |
| `token` | `{text}` | кусками, «Краткий вывод» |
| `analysis` | `{stats, map, my_case}` | один раз, после вывода |
| `queue` | `{position}` | необязательно — место в очереди на LLM |
| `error` | `{detail}` | необязательно — прерывает поиск |
| `done` | `{query_id}` | последним |

Сейчас backend отдаёт `sources` (фрагменты нормативных актов со «сырым» score
реранкера) и `token`. Фронтенд понимает и этот формат: фрагменты показываются
как документы выдачи, релевантность — sigmoid(score) в процентах. Экранам нужны судебные акты с релевантностью 0–100 и
разбором каждого дела (`facts`, `position`, `outcome`, `matches`, `diffs`, `why`,
`quote`) и полный текст акта (`full_text` — в нём ищется цитата для подсветки),
а также статистика практики и схема вывода. Это задача ML-части, а не
фронтенда.
